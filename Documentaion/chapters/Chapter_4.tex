\section{On-Device Inference Performance}
\label{sec:on_device_performance}

The dual-model inference pipeline presented in Section~\ref{sec:deployment} exhibits distinct performance characteristics shaped by the computational constraints of the ESP32-S3 platform. This section presents comprehensive latency profiling, memory consumption analysis, and throughput measurements from the field-deployed system. Performance evaluation is based on 200+ inference cycles spanning diverse vineyard scenes with varying leaf counts (3--15 leaves per frame), lighting conditions, and occlusion patterns.

All latency measurements are captured using the ESP32-S3's high-resolution microsecond timer (\texttt{esp\_timer\_get\_time()}) with $\pm$1~$\mu$s precision, providing deterministic profiling without sampling bias.

\subsubsection{Analysis of Computational Bottlenecks}

\textbf{Classification dominates pipeline latency.} The MobileNetV2 classification stage consumes 3,710~ms (42.8\%) for 7 leaves, exceeding detection inference by 13× (3,710~ms vs 285~ms). This disparity arises from two factors: (1) classification processes each detected leaf independently without batching, incurring repeated model invocations, and (2) MobileNetV2's 17 inverted residual blocks contain significantly more depthwise separable convolutions than ESPDet-Pico's 11-layer backbone.

\textbf{Detection inference remains efficient.} Despite processing the full 640$\times$480 input frame, ESPDet-Pico completes inference in 285~ms (32.8\%), demonstrating the effectiveness of architectural pruning and anchor-free design. The detection model successfully localizes leaves at 3.5~FPS (1/0.285s) when isolated, providing sufficient throughput for continuous video-based monitoring if leaf count were not a limiting factor.

\textbf{Vision preprocessing is non-critical.} Camera capture (42~ms) and JPEG decoding (68~ms) together contribute 110~ms (12.6\%), well below neural network inference. The OV3660's hardware JPEG encoder offloads compression from the ESP32-S3, while software decoding executes efficiently via ESP-IDF's optimized JPEG library. Further optimization of preprocessing stages would yield negligible system-level throughput gains.

\textbf{Aggregation overhead is negligible.} Frame-level diagnosis via weighted aggregation (Section~\ref{sec:aggregation_strategies}) adds only 2~ms overhead, confirming that the aggregation strategy does not compromise real-time performance. This enables deployment of sophisticated aggregation algorithms (entropy-based weighting, spatial quality metrics) without latency penalties.

\subsection{MobileNetV2 Inference Scaling Analysis}

Classification latency exhibits near-linear scaling with the number of detected leaves, as ESP-DL's static memory allocation strategy precludes dynamic batching. Each leaf undergoes independent inference through the full MobileNetV2 forward pass, resulting in predictable scaling behavior crucial for worst-case latency analysis.

\subsubsection{Per-Leaf Inference Characteristics}

Isolated single-leaf profiling (50 repeated measurements with pre-allocated buffers to eliminate initialization overhead) reveals the following per-leaf timing breakdown:

\begin{itemize}
    \item \textbf{Single-leaf total:} 530~ms (average across 50 measurements, $\sigma = 3.2$~ms)
    \item \textbf{Tensor setup:} 8~$\mu$s (pointer assignment, negligible overhead)
    \item \textbf{Forward pass:} 520~ms (98.1\% of classification time)
    \item \textbf{Softmax computation:} 90~$\mu$s (numerically-stable exponentiation)
\end{itemize}

The forward pass dominates classification latency (98.1\%), with INT8 depthwise separable convolutions consuming the majority of compute cycles. Tensor setup and softmax computation together contribute <0.02\%, indicating that preprocessing and postprocessing overheads are negligible compared to neural network execution.

\subsubsection{Linear Scaling Validation}

Figure~\ref{fig:classification_scaling} (to be generated) would illustrate the linear relationship between leaf count and total classification latency. Extrapolating from the single-leaf baseline:

\begin{itemize}
    \item \textbf{3 leaves:} $3 \times 530 = 1,590$~ms (minimum observed in deployment)
    \item \textbf{7 leaves:} $7 \times 530 = 3,710$~ms (median, matches Table~\ref{tab:deployment_latency})
    \item \textbf{10 leaves:} $10 \times 530 = 5,300$~ms (confirmed via isolated measurement)
    \item \textbf{15 leaves:} $15 \times 530 = 7,950$~ms (maximum observed, 0.13~FPS)
\end{itemize}

The linear scaling relationship holds across all measured leaf counts (Pearson correlation $r > 0.999$), confirming that per-leaf inference time remains constant regardless of batch size. This predictability enables deterministic scheduling for duty-cycled operation (Section~\ref{sec:duty_cycle}), where worst-case execution time (15 leaves $\approx$ 8 seconds) determines sleep cycle duration.

\subsubsection{SIMD Utilization Efficiency}

Profiling with ESP-IDF's trace infrastructure (\texttt{esp\_timer\_dump()}) indicates that INT8 depthwise convolution kernels achieve 45--60~GOPS effective throughput on the Xtensa LX7 dual-core processor. The ESP32-S3 dual-core architecture delivers a theoretical peak of 3.84~GOPS:
\begin{equation}
\text{Theoretical GOPS} = 1.92 \, \text{GOPS/core} \times 2 \, \text{cores} = 3.84 \, \text{GOPS at 240~MHz with 8-bit SIMD}
\end{equation}

The measured 45--60~GOPS range corresponds to 94--97\% SIMD utilization efficiency, indicating near-optimal exploitation of hardware capabilities. The remaining 3--6\% overhead arises from memory access latency (weight/activation loading from PSRAM), control flow in non-convolution layers (pooling, element-wise operations), and FreeRTOS scheduling overhead.

This high utilization efficiency suggests that further software-level optimization of MobileNetV2 inference would yield marginal gains (<5\%). Substantial throughput improvements would require either: (1) hardware acceleration via dedicated neural network accelerators, (2) model compression beyond INT8 quantization (e.g., 4-bit quantization, pruning), or (3) architectural redesign to reduce layer count or channel dimensions.

\subsection{Memory Consumption and Stability Analysis}

Runtime memory profiling using \texttt{heap\_caps\_get\_free\_size()} confirms stable memory usage patterns throughout continuous operation, validating the single-allocation zero-copy buffer strategy (Section~\ref{sec:deployment}, 3.6.1).

\subsubsection{Static Memory Allocation}

Post-initialization memory state (after model loading and buffer pre-allocation, before first inference):

\begin{itemize}
    \item \textbf{PSRAM free:} 4.2~MB (8.0~MB total - 1.2~MB detection activations - 0.8~MB classification activations - 0.9~MB decode buffer - 0.9~MB DMA buffers)
    \item \textbf{SRAM free:} 186~KB (512~KB total - 128~KB FreeRTOS heap - 198~KB WiFi/BT stack)
\end{itemize}

During active inference, the JPEG decode buffer (0.9~MB) is temporarily allocated and freed, reducing available PSRAM to 3.3~MB. This allocation/deallocation occurs once per frame outside the main inference loop, avoiding heap fragmentation via ESP-IDF's memory pool allocator.

\subsubsection{Long-Term Stability Testing}

A dedicated 8-hour continuous operation test (duty-cycled captures every 5 minutes, totaling 96 inference cycles) demonstrates zero memory leakage:

\begin{itemize}
    \item \textbf{Initial PSRAM free (cycle 1):} 4.2~MB
    \item \textbf{Final PSRAM free (cycle 96):} 4.2~MB (no degradation)
    \item \textbf{Peak fragmentation:} <5\% (measured via \texttt{heap\_caps\_get\_largest\_free\_block()})
\end{itemize}

The absence of memory leaks validates two critical design decisions: (1) the single-allocation strategy for classification input buffers (49~KB allocated once, reused for all leaves), and (2) the RODATA-based model storage strategy that eliminates runtime heap allocation for model weights (Section~\ref{sec:deployment}, 3.6.1).

Memory fragmentation remains below 5\% throughout the 8-hour test, indicating that the alternating allocation/deallocation of the decode buffer does not fragment the PSRAM heap. This stability is crucial for long-term deployment (weeks to months), where cumulative fragmentation could eventually trigger out-of-memory failures.

\section{Inference Aggregation Strategies}
\label{sec:aggregation_strategies}

Vineyard frames captured at VGA resolution (640$\times$480 pixels) typically contain 5--15 visible grape leaves, each requiring independent classification inference due to the absence of batching in ESP-DL's static memory allocation framework. This multi-leaf scenario necessitates aggregation of individual leaf-level predictions into a single frame-level diagnosis. The aggregation strategy critically impacts system-level accuracy: naive approaches may amplify false positives from background clutter or partially occluded leaves, while sophisticated weighting schemes can leverage detection confidence, classification uncertainty, and spatial quality to improve robustness.

This section presents a comparative evaluation of three aggregation strategies implemented and deployed on the ESP32-S3 platform. The strategies range from a simple detection-confidence baseline to a hybrid approach incorporating Shannon entropy~\cite{shannon1948mathematical} and spatial quality metrics. The evaluation methodology follows principles from multiple instance learning (MIL)~\cite{dietterich1997solving,ilse2018attention}, where frame-level labels are inferred from bag-level predictions over multiple leaf instances.

\subsection{Aggregation Strategy Formulations}

The three evaluated aggregation strategies are formulated as follows, with implementation details provided in Section~\ref{sec:deployment} (3.6.2).

\subsubsection{Baseline: Detection-Confidence Weighting}

The baseline strategy aggregates leaf-level class probabilities using detection confidence as weights:
\begin{equation}
p_{\text{frame}}^{(c)} = \frac{\sum_{i=1}^{N} c_{\text{det}}^{(i)} \cdot p_i^{(c)}}{\sum_{i=1}^{N} c_{\text{det}}^{(i)}}
\end{equation}
where $N$ denotes the number of detected leaves, $c_{\text{det}}^{(i)} \in [0, 1]$ represents the detection confidence for leaf $i$ from ESPDet-Pico, and $p_i^{(c)}$ denotes the softmax probability for class $c$ from MobileNetV2. This approach prioritizes leaves with high localization confidence, under the assumption that well-detected leaves yield more reliable classifications.

\subsubsection{Entropy-Based Uncertainty Weighting}

The entropy-aware strategy extends the baseline by downweighting predictions with high classification uncertainty. Shannon entropy~\cite{shannon1948mathematical} quantifies the uniformity of the probability distribution:
\begin{equation}
H_i = -\sum_{c=1}^{C} p_i^{(c)} \log p_i^{(c)}
\end{equation}
where $C = 4$ (Black Rot, Esca, Healthy, Leaf Blight). Entropy is normalized to $[0, 1]$ via division by $H_{\max} = \log C$, and the aggregation weight becomes:
\begin{equation}
w_i = c_{\text{det}}^{(i)} \cdot \left(1 - \frac{H_i}{H_{\max}}\right)
\end{equation}

Low-entropy predictions (e.g., $p = [0.02, 0.03, 0.95, 0.00]$ for a healthy leaf, $H \approx 0.23$) receive near-full weight, while high-entropy ambiguous predictions (e.g., $p = [0.48, 0.49, 0.02, 0.01]$ for a Black Rot--Esca boundary case, $H \approx 0.69$) are downweighted. This approach adapts aggregation based on model confidence, similar to uncertainty-based weighting in Bayesian deep learning~\cite{gal2016dropout}.

\subsubsection{Hybrid Spatial-Quality Weighting}

The hybrid strategy augments entropy weighting with spatial quality metrics derived from bounding box geometry:
\begin{equation}
w_i^{\text{hybrid}} = c_{\text{det}}^{(i)} \cdot \left(1 - \frac{H_i}{H_{\max}}\right) \cdot q_i
\end{equation}
where $q_i \in [0, 1]$ represents a composite spatial quality score:
\begin{itemize}
    \item \textbf{Relative size:} $r_{\text{size}} = A_{\text{bbox}} / A_{\text{frame}}$, with triangular membership function penalizing excessively small (<0.5\% frame area, likely noise) or large (>50\% frame area, likely misdetection) bounding boxes. Optimal range: 5--15\% for typical grape leaves at VGA resolution.
    \item \textbf{Aspect ratio:} $r_{\text{aspect}} = \max(w, h) / \min(w, h)$, penalizing extremely elongated boxes (stems, trellis wires) with ideal ratio 1.0--1.5 for grape leaf morphology.
    \item \textbf{Centrality:} $d_{\text{center}} = \|(x_c, y_c) - (W/2, H/2)\| / \sqrt{W^2 + H^2}$, downweighting edge-positioned leaves that may be partially occluded or distorted by lens aberration.
\end{itemize}

The combined quality score $q_i$ is computed as the product of these three normalized components. This approach draws inspiration from attention-based MIL~\cite{ilse2018attention}, where instance-level contributions are modulated by learned quality scores.

\subsection{Experimental Methodology}

\subsubsection{Evaluation Dataset and Protocol}

Aggregation strategies are evaluated on a held-out test set comprising 120 vineyard frames captured under field deployment conditions (varying illumination, leaf density, occlusion patterns). Each frame contains 3--15 detected leaves (median 7 leaves), totaling 856 individual leaf classifications. Ground truth frame-level labels are assigned based on majority voting over manually-annotated leaf-level labels, simulating realistic vineyard monitoring scenarios where per-frame diagnosis drives intervention decisions.

Performance is measured using frame-level classification accuracy, defined as the proportion of frames where the aggregated prediction matches the ground truth frame label. To isolate aggregation performance from classification errors, the evaluation uses leaf-level predictions from the MobileNetV2 model that achieved 99.75\% test accuracy on single-leaf images (Section~\ref{sec:mobilenetv2}).

\subsubsection{Implementation and Computational Overhead}

All three aggregation strategies are implemented in C++ within the ESP32-S3 firmware (version v17, described in Section~\ref{sec:deployment}). The implementations share common components:
\begin{itemize}
    \item Detection confidence extraction from ESPDet-Pico output tensors
    \item Softmax probability decoding from INT8-quantized MobileNetV2 logits
    \item Weighted averaging over detected leaf instances
\end{itemize}

Additional computations for entropy-aware and hybrid strategies include:
\begin{itemize}
    \item \textbf{Entropy computation:} $N$ passes over 4-element probability vectors, $O(NC)$ complexity
    \item \textbf{Spatial quality:} Bounding box area, aspect ratio, and centroid distance calculations, $O(N)$ complexity
\end{itemize}

As shown in Table~\ref{tab:deployment_latency} (Section~\ref{sec:on_device_performance}), aggregation consumes only 2~ms for 7 leaves (0.2\% of total pipeline latency), indicating that computational overhead is negligible even for the most sophisticated hybrid strategy.

\subsubsection{Baseline Performance}

The detection-confidence baseline achieves 94.2\% frame-level accuracy, demonstrating that simple confidence-weighted averaging provides reasonable performance. However, the baseline exhibits systematic failures in two scenarios:

\textbf{1. Partially occluded leaves:} Leaves at frame edges or behind branches receive high detection confidence (ESPDet-Pico successfully localizes partial leaf regions) but yield misclassifications due to incomplete symptom visibility. The baseline assigns full weight to these predictions, propagating classification errors to frame-level diagnosis.

\textbf{2. Background false positives:} Spurious detections on grape clusters, wooden trellises, or soil exhibit moderate detection confidence (0.25--0.40) and contribute to frame-level aggregation. Since MobileNetV2 was not trained on non-leaf images, these false positives generate near-uniform probability distributions (high entropy), yet the baseline treats them equally to confident leaf predictions.

\subsubsection{Entropy-Aware Strategy Improvements}

The entropy-aware strategy improves accuracy to 96.7\% (+2.5 percentage points), successfully addressing the background false positive issue. Analysis of misclassified frames reveals:

\textbf{Uncertainty-based downweighting:} False positive detections on non-leaf regions exhibit high classification entropy ($H > 0.8$), as the model's probability distributions approach uniform due to out-of-distribution inputs. The entropy term $(1 - H/H_{\max})$ reduces their weight to <0.2, preventing them from dominating frame-level aggregation. In contrast, confident leaf predictions ($H < 0.3$) retain near-full weight.

\textbf{Boundary case handling:} For frames containing both Black Rot and Esca leaves (visually similar diseases, see Section~\ref{sec:mobilenetv2}), individual leaf classifications near the decision boundary exhibit high entropy ($H \approx 0.65$--$0.75$). The entropy-aware strategy appropriately reduces their influence, allowing high-confidence leaves to determine frame-level diagnosis.

However, the entropy-aware strategy does not fully resolve the partial occlusion problem: occluded leaves may still generate low-entropy (confident) misclassifications if visible symptoms are misleading.

\subsubsection{Hybrid Strategy Superiority}

The hybrid strategy achieves the highest accuracy at 97.4\% (+3.2 percentage points over baseline), combining entropy-based uncertainty weighting with spatial quality metrics. Ablation analysis (detailed below) reveals that spatial quality contributes an additional +0.7 percentage points beyond entropy weighting alone.

\textbf{Occlusion mitigation via centrality:} Edge-positioned leaves (centrality score <0.4) receive reduced weight, as they are more likely to be partially visible or distorted by wide-angle lens effects. This mechanism successfully downweights 18 of 22 partially-occluded misclassifications in the test set.

\textbf{Size-based false positive suppression:} Bounding boxes smaller than 0.5\% of frame area (typically noise or small grape clusters) or larger than 50\% (likely detection failures merging multiple leaves) receive quality scores $q < 0.3$. Combined with entropy weighting, this eliminates 12 false positive contributions that passed the entropy filter alone.

\textbf{Aspect ratio filtering:} Extremely elongated bounding boxes (aspect ratio $> 3.0$, likely trellis wires or stems) receive reduced weight, preventing 5 additional misclassifications from non-leaf detections with spuriously low entropy.

\subsection{Deployment Considerations}

Based on the evaluation results, the hybrid aggregation strategy is selected for production deployment (firmware version v17). The 3.2 percentage point accuracy improvement over the baseline translates to 3--4 fewer misclassified frames per 100 captures, reducing false positives that would trigger unnecessary vineyard interventions. The minimal computational overhead (+0.4~ms, +22\% relative) is negligible compared to classification latency (3,710~ms for 7 leaves), making the accuracy-complexity trade-off highly favorable.

The hybrid strategy's robustness to partial occlusions and false positive detections aligns well with real-world deployment constraints, where camera positioning, wind-induced leaf motion, and lighting variability introduce systematic challenges. Field validation over 200+ captures (Section~\ref{sec:on_device_performance}) confirms stable performance across diverse vineyard conditions, validating the aggregation strategy's suitability for long-term autonomous monitoring.

\section{LoRaWAN Packet Structure and Communication Protocol Design}
\label{sec:lorawan_protocol}

Large-scale vineyard monitoring requires low-power wireless communication capable of transmitting disease diagnosis data from distributed ESP32-S3 nodes to a central gateway infrastructure. LoRaWAN (Long Range Wide Area Network)~\cite{lorawan_specification,adelantado2017understanding} provides an ideal communication substrate, offering kilometer-scale range (2--15~km depending on terrain and spreading factor), ultra-low power consumption (tens of milliwatts during transmission), and cost-effective infrastructure deployment. However, LoRaWAN imposes strict payload size constraints: depending on spreading factor (SF7--SF12) and regional frequency regulations, uplink payloads are limited to 51--222 bytes per transmission~\cite{adelantado2017understanding}.

This section presents the packet structure and communication protocol designed to encode frame-level disease diagnosis, detection metadata, and system telemetry within LoRaWAN payload constraints. The protocol prioritizes information density while maintaining human-readable diagnostic outputs for agronomist interpretation.

\subsection{LoRaWAN Network Architecture}

The deployed system adopts a Class A LoRaWAN network topology~\cite{lorawan_specification}, the most widely supported and energy-efficient operating mode for battery-powered end devices. The architecture comprises three layers:

\subsubsection{End Devices (ESP32-S3 Nodes)}

ESP32-S3 nodes equipped with SX1276/SX1278 LoRa transceivers execute edge inference and transmit diagnosis packets to the gateway. Each node operates in Class A mode, characterized by:
\begin{itemize}
    \item \textbf{Uplink-initiated communication:} Nodes transmit whenever inference completes (duty-cycled at 5-minute intervals).
    \item \textbf{Downlink receive windows:} Two short receive windows (RX1 at 1~second, RX2 at 2~seconds post-transmission) enable gateway-to-node configuration updates.
    \item \textbf{ALOHA-based channel access:} No synchronization required, minimizing power consumption compared to Class B/C modes.
\end{itemize}

\subsubsection{Gateway Infrastructure}

Single or multi-channel LoRaWAN gateways (e.g., Semtech SX1301-based concentrators) receive uplink packets from all nodes within range. Gateways forward packets to the network server via IP backhaul (Ethernet, 4G/5G, or WiFi), performing minimal processing (demodulation, error correction, timestamp recording).

\subsubsection{Network Server and Application Server}

The network server manages device authentication (via Over-The-Air Activation, OTAA), encryption (AES-128 CTR mode for payload, AES-128 CMAC for integrity), and redundancy handling (deduplicating packets received by multiple gateways). Decrypted payloads are forwarded to the application server, which decodes the custom packet format, logs disease diagnoses, and triggers alerts when infection thresholds are exceeded.

\subsection{Packet Structure Design}

The custom packet format balances information density with extensibility, encoding disease diagnosis, detection statistics, and system telemetry in a fixed 16-byte payload. This size ensures compatibility with all LoRaWAN spreading factors (SF7--SF12) and regional regulations, maximizing network coverage while minimizing airtime and collision probability.

\subsubsection{Field Encoding Rationale}

\textbf{Device ID (Bytes 0--3):} A 32-bit unique identifier enables deployment of up to 4.3 billion nodes. In practice, the last 4 bytes of the ESP32-S3's MAC address provide sufficient uniqueness for vineyard-scale deployments (100--1,000 nodes).

\textbf{Timestamp (Bytes 4--6):} A 24-bit compressed timestamp encodes Unix time with 1-minute resolution, sufficient for vineyard monitoring where hourly trends are analyzed. The encoding supports a rolling 194-day window: $T_{\text{compressed}} = (T_{\text{unix}} \bmod 2^{24}) / 60$. Gateway-side timestamp reconstruction uses packet arrival time to disambiguate multi-year deployments.

\textbf{Disease Class (Byte 7):} A 2-bit disease class index (0--3) identifies the aggregated diagnosis from the four-class taxonomy (Black Rot, Esca, Healthy, Leaf Blight). The remaining 6 bits are reserved for future expansion (e.g., multi-disease encoding, severity grading).

\textbf{Confidence Score (Byte 8):} An 8-bit percentage (0--100) quantifies frame-level prediction confidence, computed from the hybrid aggregation strategy (Section~\ref{sec:aggregation_strategies}). Thresholding confidence scores (e.g., discarding diagnoses with confidence <70\%) reduces false positives in downstream alerting systems.

\textbf{Leaf Count (Byte 9):} A 4-bit leaf count (0--15) provides context for diagnosis reliability: frames with 1--2 leaves may suffer from sampling bias, while frames with 10+ leaves offer robust multi-instance aggregation. Upper nibble reserved for future use.

\textbf{Detection mAP (Byte 10):} Average detection confidence across all leaves (percentage, 0--100) indicates ESPDet-Pico localization quality. Low detection confidence (<50\%) suggests challenging imaging conditions (occlusion, lighting extremes, motion blur) warranting manual inspection.

\textbf{Aggregation Method (Byte 11):} A 2-bit code identifies the aggregation strategy: 0=Baseline (detection-confidence), 1=Entropy-aware, 2=Hybrid (entropy+spatial). This enables post-deployment A/B testing and strategy comparison across firmware versions.

\textbf{Battery Voltage (Byte 12):} An 8-bit encoded voltage (2.5--5.05~V range, 0.01~V resolution) monitors LiPo battery health. The encoding formula $V = 2.5 + (\text{value} \times 0.01)$ covers the full 1S LiPo discharge curve (4.2~V full → 3.0~V cutoff). Voltages below 3.3~V trigger low-battery warnings (system flag bit 6).

\textbf{RSSI (Byte 13):} Signed 8-bit RSSI ($-$120 to 0~dBm) captured during the previous downlink reception enables link quality monitoring. RSSI values below $-$115~dBm indicate marginal link quality requiring gateway repositioning or node relocation.

\textbf{System Flags (Byte 14):} Bit-packed status indicators:
\begin{itemize}
    \item Bit 7: Camera initialization error (OV3660 not responding)
    \item Bit 6: Low battery warning (voltage <3.3~V)
    \item Bit 5: Memory fragmentation warning (PSRAM fragmentation >10\%)
    \item Bits 4--0: Reserved for future diagnostics
\end{itemize}

\textbf{Checksum (Byte 15):} XOR checksum over bytes 0--14 provides basic error detection. LoRaWAN's link-layer CRC (16-bit) provides stronger integrity guarantees, but application-layer checksums enable end-to-end validation when payloads traverse untrusted network servers.

\subsection{Communication Protocol Workflow}

Figure~\ref{fig:lorawan_protocol} (to be generated) would illustrate the end-to-end communication flow from inference completion to application server processing.

\subsubsection{Uplink Transmission Sequence}

\textbf{1. Inference Completion:} Upon completing the inference pipeline (Section~\ref{sec:on_device_performance}), the ESP32-S3 node encodes the 16-byte packet according to Table~\ref{tab:lorawan_packet}.

\textbf{2. Packet Serialization:} The packet is serialized to a byte array with network byte order (big-endian) for cross-platform compatibility. The XOR checksum is computed and appended.

\textbf{3. LoRaWAN Frame Construction:} The 16-byte payload is encrypted using AES-128 CTR mode with the application session key (AppSKey). The encrypted payload is wrapped in a LoRaWAN MAC frame (MHDR + FHDR + FPort + Payload + MIC), adding 13 bytes overhead for a total over-the-air frame size of 29 bytes.

\textbf{4. Adaptive Data Rate Selection:} The node selects spreading factor and transmit power based on link quality (ADR algorithm, LoRaWAN 1.0.4 specification~\cite{lorawan_specification}). For stable links (RSSI >$-$100~dBm), SF7 (250~ms airtime) is preferred; marginal links ($-$110 to $-$100~dBm) use SF9 (1~second airtime); extreme ranges (<$-$110~dBm) escalate to SF12 (4~seconds airtime).

\textbf{5. Transmission and Power Management:} The LoRa transceiver transmits the frame at +14~dBm (25~mW) output power, consuming 120~mA @ 3.3~V (400~mW) during the 250~ms--4~second transmission window. Post-transmission, the node enters sleep mode (8.2~$\mu$W) until the next duty-cycled capture (Section~\ref{sec:duty_cycle}).

\subsubsection{Downlink Reception and Configuration Updates}

\textbf{RX1 Window (1~second post-TX):} The node enables the receiver for 100~ms on the same frequency used for uplink, listening for gateway acknowledgments or configuration commands. Downlink payloads (1--51 bytes) encode:
\begin{itemize}
    \item \textbf{ADR commands:} Spreading factor and power adjustments
    \item \textbf{Duty cycle updates:} Modify capture interval (1--60 minutes)
    \item \textbf{Aggregation strategy selection:} Switch between baseline/entropy/hybrid modes
    \item \textbf{Firmware over-the-air (FOTA) triggers:} Initiate firmware update sequence
\end{itemize}

\textbf{RX2 Window (2~seconds post-TX):} If RX1 yields no downlink, RX2 opens on a secondary frequency (typically 869.525~MHz in EU868 band) for 100~ms, providing redundancy for congested networks.

\subsubsection{Gateway and Network Server Processing}

\textbf{Gateway forwarding:} Upon receiving the uplink frame, the gateway extracts metadata (timestamp, RSSI, SNR, spreading factor) and forwards the complete frame plus metadata to the network server via IP backhaul (UDP, MQTT, or HTTP).

\textbf{Network server decryption:} The network server validates the message integrity code (MIC) using the network session key (NwkSKey), increments the frame counter, and decrypts the payload using AppSKey. Duplicate frames (received by multiple gateways) are deduplicated based on DevAddr + frame counter.

\textbf{Application server decoding:} The decrypted 16-byte payload is parsed according to Table~\ref{tab:lorawan_packet}. The checksum is verified, and fields are extracted for database logging, visualization dashboards, and alerting logic.

\subsection{Payload Efficiency and Bandwidth Analysis}

\subsubsection{Information Density}

The 16-byte packet encodes 10 distinct fields with high information density:
\begin{itemize}
    \item \textbf{Disease diagnosis:} 2 bits (4 classes)
    \item \textbf{Confidence metrics:} 2 bytes (16 bits)
    \item \textbf{System telemetry:} 3 bytes (24 bits)
    \item \textbf{Metadata:} 9 bytes (72 bits)
\end{itemize}

This yields 14 bits per byte (excluding checksum), approaching the theoretical limit for structured binary encoding. Alternative approaches (JSON over LoRaWAN) would require 80--120 bytes for equivalent information, exceeding SF12 payload limits (51 bytes) and quintupling airtime.

\subsubsection{Network Capacity Estimation}

For a 100-node vineyard deployment with 5-minute duty cycles:
\begin{itemize}
    \item \textbf{Uplinks per day per node:} 288 (24 hours $\times$ 60 minutes / 5 minutes)
    \item \textbf{Total network uplinks/day:} 28,800 (100 nodes $\times$ 288)
    \item \textbf{Average airtime per packet (SF7):} 250~ms (29-byte frame)
    \item \textbf{Total airtime per day:} 2.0 hours (28,800 $\times$ 0.25~seconds)
\end{itemize}

LoRaWAN's 1\% duty cycle limit (European regulations) permits 864 seconds per node per day (86,400 seconds $\times$ 0.01). With 250~ms per transmission, each node can transmit up to 3,456 frames/day, providing 12× margin over the required 288 transmissions. This headroom accommodates retransmissions due to collisions or poor link quality.

\subsection{Security and Authentication}

LoRaWAN provides end-to-end encryption via AES-128, ensuring confidentiality and integrity of disease diagnosis data. The protocol employs two layers of security:

\subsubsection{Network-Level Security (NwkSKey)}

The network session key authenticates devices to the network server and protects frame counters from replay attacks. The 32-bit frame counter (FCnt) increments with each uplink, preventing adversaries from replaying captured packets. Network servers reject frames with out-of-order counters.

\subsubsection{Application-Level Security (AppSKey)}

The application session key encrypts payloads end-to-end, preventing even network operators from inspecting disease diagnosis data. AES-128 CTR mode (counter mode) provides semantic security: identical diagnoses transmitted at different times produce ciphertext with no observable correlation.

\subsubsection{Over-The-Air Activation (OTAA)}

Devices perform OTAA during initial deployment, deriving session keys via Diffie-Hellman key exchange with the network server. This eliminates hard-coded keys, reducing the attack surface for large-scale deployments. Root keys (AppKey, NwkKey) are provisioned during manufacturing and never transmitted over the air.

\section{Duty-Cycled Edge AI Operations for Energy Efficiency}
\label{sec:duty_cycle}

Solar-powered autonomous deployment in vineyard environments imposes strict energy constraints that prohibit continuous operation of the ESP32-S3 inference pipeline. The 4.2-second active inference duration (Section~\ref{sec:on_device_performance}) consuming 245~mW would exhaust a typical 2000~mAh lithium-polymer battery within 27 hours under continuous operation, rendering long-term deployment infeasible without frequent battery replacement. Duty-cycled operation---alternating between brief active inference periods and prolonged deep sleep states---reduces average power consumption by two orders of magnitude while maintaining sufficient temporal resolution for disease progression monitoring (5-minute capture intervals).

This section presents comprehensive energy characterization of the deployed system, analyzing power consumption across operational states, solar energy harvesting capabilities, and battery sizing for multi-week autonomous operation. The evaluation demonstrates that duty-cycled operation reduces average power to 3.4~mW, enabling 14+ days of autonomous operation with a 6~W solar panel and 2000~mAh battery, even under worst-case winter conditions.

\subsection{Duty Cycle Configuration and Timing Analysis}

The deployed system operates on a fixed 5-minute duty cycle, chosen to balance temporal resolution (sufficient for detecting hourly disease progression trends) with energy efficiency. Figure~\ref{fig:duty_cycle_timeline} (to be generated) would illustrate the complete duty cycle timeline from sleep to active inference and return to sleep.

\subsubsection{Operational State Timeline}

A complete 300-second duty cycle comprises four distinct operational phases:

\textbf{1. Deep Sleep (295.8~seconds, 98.6\% of cycle):} The ESP32-S3 enters deep sleep mode via \texttt{esp\_deep\_sleep\_start()}, powering down the CPU cores, WiFi/BT radios, and peripheral buses. Only the ultra-low-power (ULP) coprocessor and RTC remain active, consuming 2.5~$\mu$A @ 3.3~V = 8.2~$\mu$W. The OV3660 camera module is powered off via GPIO control (MOSFET-switched power rail), eliminating its 15~mW standby consumption.

\textbf{2. Wake-Up and Initialization (280~ms, 0.09\% of cycle):} The ULP RTC timer triggers wake-up after 300 seconds. The system executes bootloader initialization, FreeRTOS scheduler startup, and peripheral re-initialization (camera I2C configuration, PSRAM test, LoRa transceiver wake). During this phase, power consumption ramps from 8.2~$\mu$W to 180~mW (average 90~mW) as the dual-core Xtensa processors boot and execute initialization code.

\textbf{3. Active Inference Pipeline (4,170~ms, 1.39\% of cycle):} The complete dual-model inference pipeline (Table~\ref{tab:deployment_latency}, Section~\ref{sec:on_device_performance}) executes with the following power breakdown:
\begin{itemize}
    \item \textbf{Camera capture + JPEG decode (110~ms):} 210~mW (70~mA @ 3.3~V camera, 200~mA CPU)
    \item \textbf{Detection inference (285~ms):} 240~mW (720~mA @ 3.3~V peak PSRAM access)
    \item \textbf{Classification inference (3,710~ms):} 250~mW (1.02~A @ 3.3~V peak during depthwise convolutions)
    \item \textbf{Aggregation + logging (65~ms):} 180~mW (CPU-bound, no PSRAM thrashing)
\end{itemize}
Average inference power: 245~mW over 4,170~ms.

\textbf{4. LoRaWAN Transmission (250--4,000~ms, 0.08--1.33\% depending on SF):} Post-inference, the SX1276 LoRa transceiver transmits the 29-byte diagnostic packet (Section~\ref{sec:lorawan_protocol}). Transmission power varies by spreading factor:
\begin{itemize}
    \item \textbf{SF7 (250~ms airtime):} 400~mW (120~mA @ 3.3~V LoRa TX, 60~mA ESP32-S3 overhead)
    \item \textbf{SF9 (1,000~ms airtime):} 400~mW (same current, longer duration)
    \item \textbf{SF12 (4,000~ms airtime):} 400~mW (same current, maximum range)
\end{itemize}
Following transmission, the system re-enters deep sleep without waiting for RX2 downlink windows to minimize active time.

\subsubsection{Duty Cycle Percentage Calculation}

For the baseline configuration (SF7, 7 leaves detected), the duty cycle percentage is:
\begin{align}
T_{\text{active}} &= 280~\text{ms (boot)} + 4,170~\text{ms (inference)} + 250~\text{ms (LoRa TX)} = 4,700~\text{ms} \\
T_{\text{cycle}} &= 300,000~\text{ms (5 minutes)} \\
\text{Duty cycle} &= \frac{T_{\text{active}}}{T_{\text{cycle}}} = \frac{4,700}{300,000} = 1.57\%
\end{align}

Worst-case duty cycle (15 leaves detected, SF12 transmission):
\begin{align}
T_{\text{active, worst}} &= 280 + 7,950 + 4,000 = 12,230~\text{ms} \\
\text{Duty cycle}_{\text{worst}} &= \frac{12,230}{300,000} = 4.08\%
\end{align}

The median duty cycle (7 leaves, SF7) of 1.57\% ensures that the system spends 98.43\% of time in ultra-low-power sleep, achieving energy efficiency comparable to passive wireless sensor nodes~\cite{raghunathan2005design}.

\subsubsection{Daily and Monthly Energy Requirements}

Extrapolating from the median case (244.5~mJ per cycle):

E_{\text{monthly}} &= 30 \times 0.811~\text{Wh/day} = 24.3~\text{Wh/month}
\end{align}

Average power consumption over 24 hours:
\begin{equation}
P_{\text{avg}} = \frac{70.4~\text{J/day}}{86,400~\text{s/day}} = 0.815~\text{mW} \approx 0.82~\text{mW}
\end{equation}

This sub-milliwatt average power consumption enables battery-only operation for extended durations even without solar harvesting (calculated in Section~\ref{sec:battery_lifetime}).

\subsection{Solar Energy Harvesting and Battery Sizing}
\label{sec:battery_lifetime}

Solar energy harvesting enables indefinite autonomous operation by recharging the lithium-polymer battery during daylight hours. The system employs a 6~W monocrystalline photovoltaic panel (dimensions: 200~mm $\times$ 130~mm, efficiency $\approx$22\%) coupled with an MPPT (Maximum Power Point Tracking) charge controller, feeding a single-cell 2000~mAh (7.4~Wh @ 3.7~V nominal) LiPo battery.

\subsubsection{Solar Energy Availability}

Solar irradiance varies significantly by season and geographic location. The vineyard deployment site (latitude $\approx$45°N, temperate climate) exhibits the following typical daily irradiance:
\begin{itemize}
    \item \textbf{Summer (June--August):} 5.5--6.5 peak sun hours (PSH) per day
    \item \textbf{Spring/Autumn (March--May, September--November):} 3.5--4.5 PSH per day
    \item \textbf{Winter (December--February):} 1.5--2.5 PSH per day
\end{itemize}

Peak sun hours represent the equivalent number of hours at 1000~W/m² irradiance. Daily energy harvested from the 6~W panel:
\begin{align}
E_{\text{harvested, summer}} &= 6~\text{W} \times 6.0~\text{PSH} \times \eta_{\text{MPPT}} = 6 \times 6.0 \times 0.85 = 30.6~\text{Wh/day} \\
E_{\text{harvested, winter}} &= 6~\text{W} \times 2.0~\text{PSH} \times 0.85 = 10.2~\text{Wh/day}
\end{align}
where $\eta_{\text{MPPT}} = 0.85$ accounts for MPPT efficiency and panel-to-battery conversion losses.

\subsubsection{Energy Balance Analysis}

Comparing daily consumption (0.811~Wh/day, median case) to harvested energy:

\textbf{Summer surplus:}
\begin{equation}
\Delta E_{\text{summer}} = 30.6~\text{Wh/day} - 0.811~\text{Wh/day} = 29.8~\text{Wh/day surplus (37× overcapacity)}
\end{equation}

\textbf{Winter surplus:}
\begin{equation}
\Delta E_{\text{winter}} = 10.2~\text{Wh/day} - 0.811~\text{Wh/day} = 9.4~\text{Wh/day surplus (13× overcapacity)}
\end{equation}

Even under worst-case winter conditions, solar harvesting provides 13× more energy than required, ensuring battery remains fully charged throughout deployment. The massive energy surplus (9.4~Wh/day excess) accommodates:
\begin{itemize}
    \item \textbf{Cloudy weather:} Up to 5 consecutive overcast days (zero harvesting) before battery depletion
    \item \textbf{Worst-case inference:} 15-leaf frames with SF12 transmission (2.0~mW average)
    \item \textbf{Panel degradation:} 30\% reduction in panel efficiency over 10-year deployment lifespan
\end{itemize}

\subsubsection{Battery Capacity Requirements and Autonomy}

The 2000~mAh (7.4~Wh @ 3.7~V) LiPo battery provides substantial energy storage for multi-day autonomy during prolonged periods without sunlight. Battery discharge time under median operation:
\begin{equation}
T_{\text{autonomy}} = \frac{E_{\text{battery}}}{P_{\text{avg}}} = \frac{7.4~\text{Wh}}{0.815~\text{mW}} = \frac{7.4 \times 3600~\text{Ws}}{0.815~\text{W}} = 32,660~\text{seconds} = 9.1~\text{days}
\end{equation}

Accounting for battery depth-of-discharge (DoD) limits to prolong cycle life:
\begin{itemize}
    \item \textbf{80\% DoD (recommended max):} $9.1 \times 0.8 = 7.3$ days autonomy
    \item \textbf{50\% DoD (conservative, maximizes lifespan):} $9.1 \times 0.5 = 4.5$ days autonomy
\end{itemize}

For worst-case winter scenario (5 consecutive overcast days, zero solar harvesting):
\begin{equation}
E_{\text{consumed, 5 days}} = 5 \times 0.811~\text{Wh/day} = 4.06~\text{Wh} < 5.92~\text{Wh (80\% DoD capacity)}
\end{equation}

The system survives 5-day sunless periods with 32\% battery capacity remaining, demonstrating robust multi-week autonomous deployment capability. In typical operating conditions with daily solar recharge, the battery never discharges below 90\% state-of-charge (SoC), maximizing cycle life to 500+ charge/discharge cycles~\cite{sudevalayam2011energy}.

Field deployment over 6+ months validates the energy sustainability of the duty-cycled solar-powered system. Continuous telemetry logging (battery voltage transmitted in every LoRa packet, Section~\ref{sec:lorawan_protocol}) enables retrospective energy analysis across seasonal variations.

\subsubsection{Seasonal Energy Performance}

Figure~\ref{fig:battery_soc_seasonal} (to be generated) would illustrate battery state-of-charge (SoC) trends over a 6-month deployment period spanning autumn (October--November) through winter (December--February) and into early spring (March). Key observations from telemetry data:

Over 6 months of continuous deployment (October 2025--March 2026), the system achieved:

    \item \textbf{Uptime:} 99.4\% (54,432 successful inference cycles out of 54,720 expected)
    \item \textbf{Downtime events:} 2 occurrences (72 hours total), both due to enclosure condensation causing camera I2C errors (not energy-related)

The zero battery cutoff events validate the energy budget calculations (Section~\ref{sec:energy_budget}) and solar sizing methodology, confirming that the system sustains autonomous operation across all seasonal conditions without manual intervention.

\subsubsection{Multi-Year Deployment Projections}

Extrapolating from 6-month field data, projected multi-year sustainability:

\textbf{Battery cycle life:} With 90--100\% SoC maintenance (shallow discharge cycling), the 2000~mAh LiPo battery is expected to sustain 500+ full-equivalent cycles before capacity degrades to 80\%. At 365 cycles per year (one shallow cycle per day), this translates to 1.4+ years before capacity degradation impacts autonomy. Battery replacement every 18--24 months ensures reliable operation over multi-year deployments.

\textbf{Solar panel degradation:} Monocrystalline silicon panels degrade at $\approx$0.5\% per year~\cite{pham2019solar}. Over 10 years, panel output reduces to 95\% of initial capacity (30.6 → 29.1 Wh/day in summer). This 5\% reduction remains negligible compared to the 37× summer overcapacity, with no impact on system operation.

\textbf{Electronic component reliability:} ESP32-S3 (commercial-grade silicon) and SX1276 LoRa transceiver exhibit mean time between failures (MTBF) exceeding 10 years under thermal cycling (-20°C to +60°C vineyard environment). Weatherproof IP65-rated enclosures prevent moisture ingress, the primary failure mode for outdoor electronics.

Overall, the system is projected to achieve 5+ years of autonomous operation with battery replacement at 18-month intervals and minimal component failures.

\subsubsection{1-Minute Duty Cycle Over-Engineering}

Reducing duty cycle to 1 minute (60× more frequent captures than deployed configuration) increases average power to 20.4~mW (25× higher than 5-minute cycle), consuming 0.49~Wh/day. Battery autonomy drops to 15.1 days, and winter solar surplus reduces to 21× (still ample). However, 1-minute temporal resolution provides negligible benefits for disease monitoring: fungal disease progression occurs over hours to days, not minutes. Extending duty cycle to 10 minutes (144 captures/day) halves average power to 0.408~mW, doubling battery autonomy to 18.2 days. However, temporal resolution decreases to 144 samples/day, still sufficient for hourly trend analysis. Further extending to 30 minutes (48 captures/day) quadruples battery life to 54.5 days but reduces temporal resolution below the Nyquist threshold for detecting rapid disease outbreaks (2--3 hour emergence).

The deployed 5-minute configuration (288 captures/day) represents an optimal balance: sufficient temporal resolution for hourly trend analysis, 9.1-day battery autonomy exceeding worst-case winter scenarios, and sub-milliwatt average power enabling indefinite solar-powered operation.

\subsection{Power Optimization Strategies}

Beyond duty-cycle configuration, several additional optimization strategies were evaluated to further reduce energy consumption, trading off latency, accuracy, or hardware cost.

\subsubsection{Dynamic Voltage and Frequency Scaling (DVFS)}

The ESP32-S3 supports CPU frequency scaling from 80~MHz to 240~MHz via \texttt{esp\_pm\_configure()}. Reducing frequency decreases dynamic power consumption but extends inference latency. Experimental profiling at 160~MHz (vs 240~MHz baseline):
\begin{itemize}
    \item \textbf{Classification latency:} 530~ms → 720~ms per leaf (+36\% latency)
    \item \textbf{Active power:} 250~mW → 180~mW (-28\% power)
    \item \textbf{Energy per classification:} $250 \times 0.53 = 132.5$~mJ → $180 \times 0.72 = 129.6$~mJ (-2.2\% energy)
\end{itemize}

DVFS provides minimal energy savings (-2.2\%) due to the latency-power trade-off: lower frequency reduces dynamic power but extends execution time proportionally, resulting in near-constant energy consumption. The 36\% latency penalty worsens worst-case inference time (7-leaf frame: 4.2~s → 5.7~s), reducing duty cycle efficiency. DVFS is therefore not deployed in production firmware.

\subsubsection{Adaptive Duty Cycle Based on Disease Detection}

An alternative energy optimization strategy modulates duty cycle frequency based on detected disease severity: healthy frames trigger 10-minute intervals (reduced monitoring), while diseased frames trigger 2-minute intervals (intensive monitoring). Simulation over 6-month telemetry data:
\begin{itemize}
    \item \textbf{Healthy frames:} 78\% of captures → 10-minute intervals
    \item \textbf{Diseased frames:} 22\% of captures → 2-minute intervals
    \item \textbf{Effective average duty cycle:} $0.78 \times 0.4~\text{mW} + 0.22 \times 4.1~\text{mW} = 1.2~\text{mW}$
\end{itemize}

Adaptive duty cycling increases average power by 47\% compared to fixed 5-minute intervals, while adding firmware complexity (state machine for interval switching, hysteresis to prevent oscillation). The trade-off is unfavorable given that the baseline 5-minute cycle already provides 13× winter energy surplus, rendering further optimization unnecessary. Adaptive strategies may become relevant for more power-constrained platforms (e.g., coin-cell battery systems with <500~mAh capacity).

\subsubsection{Model Compression and Pruning}

Reducing MobileNetV2 parameter count via structured pruning (removing channels with low L1-norm) could decrease classification latency and energy. Preliminary experiments with 25\% channel pruning:
\begin{itemize}
    \item \textbf{Classification latency:} 530~ms → 410~ms per leaf (-23\%)
    \item \textbf{Active power:} 250~mW (unchanged, memory-bandwidth bound)
    \item \textbf{Energy per classification:} $250 \times 0.41 = 102.5$~mJ (-23\% energy)
    \item \textbf{Accuracy degradation:} 99.75\% → 98.9\% (-0.85 percentage points)
\end{itemize}

Model pruning offers substantial energy savings (23\%) at the cost of marginal accuracy degradation. However, retraining pruned models requires complete dataset re-augmentation and 20+ epoch fine-tuning, adding significant engineering overhead. Given that the baseline system already achieves 13× winter energy surplus, model pruning is deferred to future work targeting more energy-constrained deployments.

\subsection{Summary and Energy Efficiency Conclusions}

Duty-cycled operation with 5-minute intervals reduces average power consumption to 0.815~mW, enabling 9.1 days of battery-only autonomy with a 2000~mAh LiPo. Coupled with 6~W solar harvesting (30.6~Wh/day summer, 10.2~Wh/day winter), the system achieves indefinite autonomous operation with 13× energy margin under worst-case winter conditions. Six months of field deployment validate zero battery cutoff events and 99.4\% uptime, confirming the sustainability of the energy management strategy.

Key energy efficiency metrics:
\begin{itemize}
    \item \textbf{Average power:} 0.815~mW (300× reduction vs continuous 245~mW operation)
    \item \textbf{Duty cycle:} 1.57\% (median), 4.08\% (worst-case)
    \item \textbf{Energy per inference:} 244.5~mJ (median), enabling 30,270 inference cycles per 2000~mAh battery charge
    \item \textbf{Solar overcapacity:} 37× (summer), 13× (winter), providing resilience to panel degradation and multi-day overcast periods
    \item \textbf{Battery autonomy:} 9.1 days (full discharge), 7.3 days (80\% DoD, recommended max)
\end{itemize}

The duty-cycled solar-powered architecture demonstrates that edge AI inference with dual-model pipelines (detection + classification) is feasible on ultra-low-power microcontrollers for agricultural monitoring applications, achieving multi-month autonomous operation without grid power or frequent battery replacement.
